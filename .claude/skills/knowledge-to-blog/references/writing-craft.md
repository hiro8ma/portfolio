# 技術記事の書き方の型

技術記事の書き方の教材から取り込んだ規範を、執筆の段階ごとにまとめる。
`structure.md` は測定ノートを記事に変える型、`zenn.md` は Zenn の記法を扱う。
このファイルは、どの記事にも共通する書き方を扱う。
最後の「公開前の確認」は、記事を渡す前に毎回すべて確かめる。

## 1. ネタと記事の型を選ぶ

日々のトラブル、疑問、発見はどれも記事の材料になる。
ネタは「書きやすさ」と「反響の得やすさ」の 2 軸で考え、型ごとに釣り合いが違うことを前提にする。

| 型 | 喜ぶ読み手 | 生成 AI に代わられやすいか |
| --- | --- | --- |
| トラブルシューティング | 同じエラーに遭遇した人 | 代わられやすい |
| How-To | 同じことをこれから作る人 | 代わられやすい |
| ツールやライブラリの新機能紹介 | 新機能を手早く知りたい人 | 代わられやすい |
| 海外の記事や OSS の告知の日本語での紹介 | 英語の一次情報を追えていない人 | 代わられやすい |
| 難しい分野の入門、学習方法 | これから学ぶ初心者 | 代わられやすい |
| コードレビューで受けた、またはよくする指摘 | 同じ書き方をしている人。レビューで同じ説明を繰り返す代わりにリンクを渡せる | 代わられにくい |
| ツールの TIPS、便利な使い方 | 同じツールを使う人 | 代わられにくい |
| やってみた、使ってみた | 流行の技術で何ができ、使い心地はどうかを知りたい人 | 代わられにくい |
| 技術書の書評 | その本を買うか迷っている人。要約ではなく自分の感じたことを中心にする | 代わられにくい |
| 開発報告、運用の工夫、現場の体験談 | 同じ問題を抱える人。問題、工夫、結果の順。失敗も材料になる | 代わられにくい |
| 技術エッセイ、主張の強いポエム | 同じ立場で考えている人。賛否が出る前提で書く | 代わられにくい |
| カンファレンスや勉強会の参加レポート | 参加できなかった人。発表の羅列ではなく自分の学びを足す | 代わられにくい |
| SNS に書こうとして長くなった内容 | フォロワーと、後から検索する人 | 代わられにくい |

代わられやすい型でも、生成 AI の回答や資料をきっかけに、実装を読む、公式ドキュメントを調べる、動かして確かめる、回答との違いを見つける、まで進めれば、その過程と発見が記事の価値になる。
100 個の機能を訳すより、全部試して 5 個を選び、理由と使用感を書く方が書き手にしか書けない記事になる。

## 2. 書く前に調べ、骨組みを作る

簡単だと思うテーマでも、書く前に下調べをする。

- 公式ドキュメントを読み、自分の理解と一致しているか確かめる
- 小さいサンプルを動かし、予想どおりに動くか確かめる
- ライブラリのコードを読み、なぜその挙動になるか確かめる
- 仕様が変わった理由は、GitHub の Issue とプルリクエストで確かめる

調べる途中で「なぜそうなっているのか」という問いが出たら、記事の軸をその問いに移すことを検討する。

内容がまだ曖昧なら、マインドマップで広げてから絞る。
中央にテーマを置き、関連する話題を枝として伸ばし、さらに細かい話題を派生させ、必要なものを選んで記事の形に近づける。
長くなりそうなら、本文の前に「書きたいことの一覧」を作り、見出しの親子関係を決める。

書く順番は読む順番と同じでなくてよい。
本文を思うままに書き、読み直して見出しを付け、全体に合わせてはじめにとまとめを書き、最後にタイトルを決める、でよい。

## 3. 自分の言葉で書く

技術書や他人の記事、生成 AI の回答を写して並べた記事は、自分のアウトプットにならない。
学んだことを記事にするときは、自分の言葉で説明し、自分で試した結果と、自分の経験や判断を加え、元の情報と違う整理の軸を持たせる。
個人の学習記録が目的なら、公開せずに非公開のメモとして残す。

書いた後、何も見ずに第三者へその内容を説明できるかを試す。
説明に詰まる箇所は、理解が足りない箇所なので、調べ直してから書き直す。

## 4. 良い記事の 4 条件

- わかりやすい
- 技術的に正確である
- 根拠をたどれる（公式ドキュメント、GitHub のソース、参考にした本や記事へのリンクを置く）
- 独自性がある（自分で調べたこと、動かした結果、経験、整理と判断のどれかを核にする）

## 5. 読み手を思い浮かべる

1. 読み手を 1 人決める。熟練者か初心者か、何に困っているか。「その技術を知らなかった数か月前の自分」は有効
2. その読み手の前提知識、知りたいこと、つまずきそうな箇所を想定して書く
3. 書き終えたら、その読み手の立場で読み直す。前提知識が足りないか、説明が飛んでいないか、初めて読む人に分かるか
4. 「この読み手なら喜ぶ」と言えるまで読み直してから公開する

## 6. 構成の型

エラーを解決した記事は、次の順で書く。

```
はじめに / 実行環境 / 発生したエラー / エラーの原因 / 解決方法 / まとめ / 参考文献
```

実装を紹介する記事は、次の順で書く。

```
はじめに / 実行環境 / やりたかったこと / 実現方法 / まとめ / 参考文献
```

型は固定ではなく、記事の種類に合わせて組み替える。

- はじめに：何を説明し、読むと何が分かり、誰向けで、前提知識は何かを書く。初心者向けならそう書く。読み手はここで自分に要る記事かを判断する
- 実行環境：言語、ライブラリ、ツール、OS、ブラウザのバージョンを書く。時間がたつと挙動が変わるので、違うバージョンの読み手が注意点を判断できるようにする
- 発生したエラー：エラーメッセージを加工せずに貼る。同じエラーで検索した読み手がたどり着ける
- 原因：なぜ起きたかを書く。動いた手順だけで終えない
- やりたかったこと：実装の目的と、変更前の問題を具体的に書く
- 実現方法：コードと、なぜそれで解決するかを書く
- まとめ：目的地に着いたことを示す。何が分かったかを短く言い直し、「説明しました」で終えず読み手が得たものを書く
- 参考文献：参考にした Issue、記事、本をリンクで残す

タイトル、はじめに、まとめは同じ主題を扱う。書く途中で主題が変わったら、3 つとも最終的な中身に合わせて直す。
長く複雑な記事には、冒頭に TL;DR を 3〜5 個の箇条書きで置く。結論を先に知ってから詳細を読む方が理解しやすい。

## 7. 見出し

- 見出しは本文を意味の単位に分け、拾い読みと、後で戻ったときの目印になる。見出しだけを追えば概要が分かるようにする
- 疑問形の見出し（「なんで bin/ がいらないの？」）は、答えを読みたくさせる
- 結論や注意点を見出しに込めると、全部読まなくても要点が伝わる
- 300〜500 字に 1 つを目安にする。コードや画像で文章が途切れる箇所は、この頻度でなくてよい
- 本文は `##` と `###` で組み、階層を飛ばさない。文字を大きくする目的で使わない
- 1〜2 行に収める。短くするために意味を削らない

## 8. タイトル

- 読まなくても何の記事か想像できる具体さにする（「RSpec のエラー」ではなく「RSpec 実行時に Webdrivers::VersionError が発生する場合の対処方法」）
- 読むと得られるもの（分かること、できること）を入れる
- 数値（何か月、何選）と対象読者（「JS 初心者」）を入れると、情報量と誰向けかが伝わる
- 対象の技術名を入れる。一般的な概念の記事は【Ruby】のように技術名を明示する
- 伝えたいことを前半に置く。一覧や SNS では後半が省略される
- 本文が応えられない煽り（「知らないと損」「これ使ってないやつは損してる」「小学生でも分かる」）は付けない
- 人気の記事のタイトルは 16〜34 文字、平均 27 文字程度の例が多いが、文字数は目安であって規則ではない
- 本文を書き終えてから、本文の要約として決め直す

## 9. 見せ方

- コードの前後に、何を実現するコードか、どこを見るか、変更前後で何が変わったか、なぜこの書き方かを書く
- コードと本文の割合は、文字数で半々前後を目安にする。コードだけ、説明だけ、の両方を避ける
- 画面の操作や UI の状態はスクリーンショットにする。見せたい範囲に絞り、文字が読める大きさで撮る。縦に長い画像は折りたたむ
- 時間の変化そのものを見せたいときだけ、動画か短い GIF にする。GIF は範囲と解像度を絞る
- 抽象的な関係は図にする
- コードは原則テキストで載せる。書き込みで示したいときだけ補助的に画像にし、テキストのコードも残す
- 画像には代替テキストを付ける
- 抽象的な主張は、書き手の実体験（何をして、何が起き、何が分かったか）に落として具体例にする
- 測った事実を伝える記事では、本文中の絵文字と口語（「ハマる」「〜ですよね」）を外し、観測と判断をそのまま書く

## 10. Markdown の書き方

投稿先で使える記法は違うので、最後は投稿先の仕様を確かめる。

- 見出しは `##` から始める。`#` は記事のタイトルに使われる
- 箇条書きはハイフン、コードはバッククォート 3 つで囲み、言語名を付けて色を付ける
- 本文中の変数名やメソッド名はバッククォート 1 つで囲む
- リンクは `[表示する文字](URL)` で書く。URL だけを 1 行に置くと、Zenn や Qiita ではリンクカードになる
- 段落は空行で分ける。単なる改行の扱いはサービスで違う

## 11. 正しい情報を正しく伝える

誤った情報を書くと、読んだ人がそれを使い、さらに広げる。技術情報はネットで再利用されやすいので、書き手と読み手の両方が損をする。
記事にするのは「自分が見つけた情報」ではなく、「いまの対象の環境について根拠を確かめた情報」にする。

公式の情報源を確かめる。

- 誰かの記事で解決したときも、公式の情報で、その方法の意味、制約、副作用（性能の低下など）を確かめる
- 生成 AI の回答も正しいとは限らないので、公式の情報で確かめてから使う

OSS なら、コード、Issue、プルリクエストまで確かめる。

- コードを読み、必要ならデバッグ実行して、なぜその処理になるか、何が原因でエラーになるか、どの条件で挙動が変わるかを確かめる
- Issue とプルリクエストで、困っている人の議論、仕様変更の理由、バグ修正の背景、実装上の判断を確かめる

情報の日付とバージョンを確かめる。

- 参考にした記事の投稿日、更新日、対象バージョンを見て、「当時の情報がいまも有効か」を公式の情報と照らし合わせる（例：Ruby の DateTime は 2.5 以降で非推奨で、Time が推奨されている）
- 記事で説明する挙動は、どのバージョンで確かめたか、どのバージョンから変わったか、いまのバージョンではどうかを、分かる範囲で書く
- 実行環境とバージョンを明記する。すべての記事を最新に保つのは難しいので、将来の読み手に「いまの環境とは違うかもしれない」と伝えるために書く

一次情報とそれ以外を区別する。

- 一次情報：公式ドキュメント、ライブラリの README、開発者自身のブログ。GitHub の Issue とプルリクエストもそれに近い
- 一次情報以外：Qiita や Zenn の記事、個人ブログ、生成 AI の回答。更新されずに古くなることがある
- 一次情報なら必ず正しい、それ以外なら必ず誤り、ではない。一次情報以外だけに頼らず、できるだけ一次情報までさかのぼる

参考文献のリンクを残す。

- 読み手が、さらに調べる、別の情報源と照らし合わせる、公式で正しさを確かめる、原典から追加の情報を得る、をできるようにする
- どの情報を参考にしたかを明らかにする。記事の末尾にまとめても、関係する箇所の直後に置いてもよい

その技術に詳しい人がいれば、公開前にレビューを頼む。理解が合っているか、誤解を招かないか、より正確な言い方がないかを聞く。必須ではない。

調べ尽くしても断定できない部分は、不確かであることを書く（例：「この方法が最善か自信がないので、よい方法があればコメントで教えてください」）。
ただし、断り書きは誤りを書いてよい理由にはならない。調べたうえで判断できない箇所に限って使う。公開後に誤りを指摘されたら、確かめて直す。

固有名詞は公式の表記に合わせる（JAVA ではなく Java、Github ではなく GitHub、VisualStudio Code ではなく Visual Studio Code、Mac OS ではなく macOS）。迷ったら公式サイトで確かめる。表記の誤りは記事全体の信頼を下げる。

他の記事、本、公式ドキュメントの文章を使うときは引用として扱う。

- 引用部分を `>` で囲み、自分の文章と区別する
- 元の文章を改変しない
- 出典（タイトルとリンク）を書く
- 記事の主体は自分の文章にし、引用を主体にしない

公開前は、次の順に確かめる。

1. 記事の中の技術的な主張を洗い出す
2. 公式ドキュメント、README、ソースコードなどの一次情報で確かめる
3. 必要なら Issue とプルリクエストで背景や変更の理由を確かめる
4. 参考にした記事の投稿日と対象バージョンを確かめる
5. 自分の環境で動かして確かめる
6. 実行環境と対象バージョンを記事に書く
7. 参考にした情報源へのリンクを残す
8. 不確かな箇所は、その範囲を書く
9. できれば詳しい人にレビューを頼む
10. 固有名詞の公式の表記を確かめる

## 12. 公開前の確認

- 誤字や明らかな誤りがないか
- 読み手が理解しにくい箇所がないか（`reader-test` で、書いた文脈を持たない読み手として読ませる）
- 検索や SNS で記事を見つけた第三者が読んでも分かるか
- 書いた直後は自分の文章を客観的に読みにくいので、できれば時間を置いて読み直す
- タイトル、はじめに、まとめが同じ主題か
- トピック（Qiita ならタグ）に、扱った言語、フレームワーク、ライブラリの名前を入れたか。トピックをフォローしている読み手に届く
- 4 条件（わかりやすい、正確、根拠をたどれる、独自性）を満たすか
- 11 の確認の順番（技術的な主張の洗い出しから、固有名詞の表記まで）を終えたか
- PC とスマートフォンの両方で表示を確かめたか

## 13. 公開した後

- 自分の記事を読み直して気づいた点を直す
- 反応を見て、必要なら内容を更新する
- SNS やコミュニティで共有する。適切なトピックを付けるだけでも一定の読み手に届く
- 他の人の技術記事を読み、参考になったものにはリアクションを返す

公開を終わりではなく、反応を受けて次の記事につなげる循環として扱う。
