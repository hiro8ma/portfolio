# 技術記事の書き方の型

技術記事の書き方の教材から取り込んだ規範を、執筆の段階ごとにまとめる。
`structure.md` は測定ノートを記事に変える型、`zenn.md` は Zenn の記法を扱う。
このファイルは、どの記事にも共通する書き方を扱う。
最後の「公開前の確認」は、記事を渡す前に毎回すべて確かめる。

## 1. ネタと記事の型を選ぶ

日々のトラブル、疑問、発見はどれも記事の材料になる。
ネタは「書きやすさ」と「反響の得やすさ」の 2 軸で考え、型ごとに釣り合いが違うことを前提にする。

| 型 | 喜ぶ読み手 | 生成 AI に代わられやすいか |
| --- | --- | --- |
| トラブルシューティング | 同じエラーに遭遇した人 | 代わられやすい |
| How-To | 同じことをこれから作る人 | 代わられやすい |
| ツールやライブラリの新機能紹介 | 新機能を手早く知りたい人 | 代わられやすい |
| 海外の記事や OSS の告知の日本語での紹介 | 英語の一次情報を追えていない人 | 代わられやすい |
| 難しい分野の入門、学習方法 | これから学ぶ初心者 | 代わられやすい |
| コードレビューで受けた、またはよくする指摘 | 同じ書き方をしている人。レビューで同じ説明を繰り返す代わりにリンクを渡せる | 代わられにくい |
| ツールの TIPS、便利な使い方 | 同じツールを使う人 | 代わられにくい |
| やってみた、使ってみた | 流行の技術で何ができ、使い心地はどうかを知りたい人 | 代わられにくい |
| 技術書の書評 | その本を買うか迷っている人。要約ではなく自分の感じたことを中心にする | 代わられにくい |
| 開発報告、運用の工夫、現場の体験談 | 同じ問題を抱える人。問題、工夫、結果の順。失敗も材料になる | 代わられにくい |
| 技術エッセイ、主張の強いポエム | 同じ立場で考えている人。賛否が出る前提で書く | 代わられにくい |
| カンファレンスや勉強会の参加レポート | 参加できなかった人。発表の羅列ではなく自分の学びを足す | 代わられにくい |
| SNS に書こうとして長くなった内容 | フォロワーと、後から検索する人 | 代わられにくい |

代わられやすい型でも、生成 AI の回答や資料をきっかけに、実装を読む、公式ドキュメントを調べる、動かして確かめる、回答との違いを見つける、まで進めれば、その過程と発見が記事の価値になる。
100 個の機能を訳すより、全部試して 5 個を選び、理由と使用感を書く方が書き手にしか書けない記事になる。

## 2. 書く前に調べ、骨組みを作る

簡単だと思うテーマでも、書く前に下調べをする。

- 公式ドキュメントを読み、自分の理解と一致しているか確かめる
- 小さいサンプルを動かし、予想どおりに動くか確かめる
- ライブラリのコードを読み、なぜその挙動になるか確かめる
- 仕様が変わった理由は、GitHub の Issue とプルリクエストで確かめる

調べる途中で「なぜそうなっているのか」という問いが出たら、記事の軸をその問いに移すことを検討する。

内容がまだ曖昧なら、マインドマップで広げてから絞る。
中央にテーマを置き、関連する話題を枝として伸ばし、さらに細かい話題を派生させ、必要なものを選んで記事の形に近づける。
長くなりそうなら、本文の前に「書きたいことの一覧」を作り、見出しの親子関係を決める。

書く順番は読む順番と同じでなくてよい。
本文を思うままに書き、読み直して見出しを付け、全体に合わせてはじめにとまとめを書き、最後にタイトルを決める、でよい。

## 3. 自分の言葉で書く

技術書や他人の記事、生成 AI の回答を写して並べた記事は、自分のアウトプットにならない。
学んだことを記事にするときは、自分の言葉で説明し、自分で試した結果と、自分の経験や判断を加え、元の情報と違う整理の軸を持たせる。
個人の学習記録が目的なら、公開せずに非公開のメモとして残す。

書いた後、何も見ずに第三者へその内容を説明できるかを試す。
説明に詰まる箇所は、理解が足りない箇所なので、調べ直してから書き直す。

## 4. 良い記事の 4 条件

- わかりやすい
- 技術的に正確である
- 根拠をたどれる（公式ドキュメント、GitHub のソース、参考にした本や記事へのリンクを置く）
- 独自性がある（自分で調べたこと、動かした結果、経験、整理と判断のどれかを核にする）

## 5. 読み手を思い浮かべる

1. 読み手を 1 人決める。熟練者か初心者か、何に困っているか。「その技術を知らなかった数か月前の自分」は有効
2. その読み手の前提知識、知りたいこと、つまずきそうな箇所を想定して書く
3. 書き終えたら、その読み手の立場で読み直す。前提知識が足りないか、説明が飛んでいないか、初めて読む人に分かるか
4. 「この読み手なら喜ぶ」と言えるまで読み直してから公開する

## 6. 構成の型

エラーを解決した記事は、次の順で書く。

```
はじめに / 実行環境 / 発生したエラー / エラーの原因 / 解決方法 / まとめ / 参考文献
```

実装を紹介する記事は、次の順で書く。

```
はじめに / 実行環境 / やりたかったこと / 実現方法 / まとめ / 参考文献
```

型は固定ではなく、記事の種類に合わせて組み替える。

- はじめに：何を説明し、読むと何が分かり、誰向けで、前提知識は何かを書く。初心者向けならそう書く。読み手はここで自分に要る記事かを判断する
- 実行環境：言語、ライブラリ、ツール、OS、ブラウザのバージョンを書く。時間がたつと挙動が変わるので、違うバージョンの読み手が注意点を判断できるようにする
- 発生したエラー：エラーメッセージを加工せずに貼る。同じエラーで検索した読み手がたどり着ける
- 原因：なぜ起きたかを書く。動いた手順だけで終えない
- やりたかったこと：実装の目的と、変更前の問題を具体的に書く
- 実現方法：コードと、なぜそれで解決するかを書く
- まとめ：目的地に着いたことを示す。何が分かったかを短く言い直し、「説明しました」で終えず読み手が得たものを書く
- 参考文献：参考にした Issue、記事、本をリンクで残す

タイトル、はじめに、まとめは同じ主題を扱う。書く途中で主題が変わったら、3 つとも最終的な中身に合わせて直す。
長く複雑な記事には、冒頭に TL;DR を 3〜5 個の箇条書きで置く。結論を先に知ってから詳細を読む方が理解しやすい。

## 7. 見出し

- 見出しは本文を意味の単位に分け、拾い読みと、後で戻ったときの目印になる。見出しだけを追えば概要が分かるようにする
- 疑問形の見出し（「なんで bin/ がいらないの？」）は、答えを読みたくさせる
- 結論や注意点を見出しに込めると、全部読まなくても要点が伝わる
- 300〜500 字に 1 つを目安にする。コードや画像で文章が途切れる箇所は、この頻度でなくてよい
- 本文は `##` と `###` で組み、階層を飛ばさない。文字を大きくする目的で使わない
- 1〜2 行に収める。短くするために意味を削らない

## 8. タイトル

- 読まなくても何の記事か想像できる具体さにする（「RSpec のエラー」ではなく「RSpec 実行時に Webdrivers::VersionError が発生する場合の対処方法」）
- 読むと得られるもの（分かること、できること）を入れる
- 数値（何か月、何選）と対象読者（「JS 初心者」）を入れると、情報量と誰向けかが伝わる
- 対象の技術名を入れる。一般的な概念の記事は【Ruby】のように技術名を明示する
- 伝えたいことを前半に置く。一覧や SNS では後半が省略される
- 本文が応えられない煽り（「知らないと損」「これ使ってないやつは損してる」「小学生でも分かる」）は付けない
- 人気の記事のタイトルは 16〜34 文字、平均 27 文字程度の例が多いが、文字数は目安であって規則ではない
- 本文を書き終えてから、本文の要約として決め直す

## 9. 見せ方

- コードの前後に、何を実現するコードか、どこを見るか、変更前後で何が変わったか、なぜこの書き方かを書く
- コードと本文の割合は、文字数で半々前後を目安にする。コードだけ、説明だけ、の両方を避ける
- 画面の操作や UI の状態、操作の前後の違い、ブラウザの表示、コードの変更による画面の変化はスクリーンショットにする。見せたい範囲に絞り、文字が読める大きさで撮る。縦に長い画像は折りたたむ
- 時間の変化そのものを見せたいときだけ、動画か短い GIF にする。GIF は範囲と解像度を絞る
- 抽象的な関係は図にする
- コードは原則テキストで載せる。書き込みで示したいときだけ補助的に画像にし、テキストのコードも残す
- 画像には代替テキストを付ける
- 抽象的な主張は、書き手の実体験（何をして、何が起き、何が分かったか）に落として具体例にする
- 測った事実を伝える記事では、本文中の絵文字と口語（「ハマる」「〜ですよね」）を外し、観測と判断をそのまま書く

文の読みやすさ（文体の統一、長い文の分割、主語と述語、漢字を開く、補助動詞、結論を先に、「が」は逆接だけ、逆接と同じ文末を続けない、根拠のある内容を弱めない）は、`japanese-tech-writing` の「文の読みやすさ」に従う。
文章の技術を守ることを目的にしない。伝えたいことがあり、主題が一貫し、読み手が意味を追え、誤解しにくいことを優先する。

## 9-2. コードの載せ方

- 嘘をつかない。関数名と処理を一致させ（掛け算なのに `add` と名付けない）、載せるコードは実際に動かして期待どおりの結果になることを確かめる。頭の中で作ったコードや、編集画面に直接打ち込んだコードは間違いが入りやすい
- 実在するフレームワークのコードに見える疑似コードは書かない（Rails の例で `redirect_for` のような実在しない API を混ぜない）。説明のために架空の関数や API を使うときは、疑似コードであること、または仮の名前であることをはっきり書く
- 結果が直感的でない処理は、コードと実行結果をセットで載せる（`#=> "#043c78"` のように）
- 本や Web のコードを参考にしたら、コードのコメントか本文に出典を書く
- エラーメッセージとスタックトレースは画像にせず、テキストで載せる。コピーでき、検索でき、欠けにくい。エラー画面の見た目も要るときは、画像とテキストの両方を載せる
- 本文中の変数名、メソッド名、短いコマンドはコードスパン（バッククォート 1 つ）で囲む。複数行のコードや長いコマンドはコードブロックにする。コードスパンに長いコードを入れると横スクロールが出る
- コードブロックでも 1 行が長すぎるなら、構文上問題のない位置で改行し、横スクロールを減らす
- シンタックスハイライトは中身に合う言語を指定する（ERB に HTML を指定しない。JavaScript、TypeScript、JSX を区別する）
- エラーメッセージ、スタックトレース、ターミナルの出力、ターミナルで打つコマンド、ログは、ハイライトを付けない方が読みやすいことがある。サンプルコード、HTML、SQL、YAML、JSON、XML は言語を指定する
- 文章とコードは「文章 → コード → 文章 → コード」と交互に置く
- 言語、フレームワーク、ライブラリ、OS に加えて、SQL なら RDBMS の種類とバージョンを書く。SQL は方言があり、たとえば `IFNULL` は MySQL と SQLite では使えるが、PostgreSQL と Oracle では使えない
- 問題やエラーを説明するときは、読み手が原因と解決を理解できるだけのコードとスタックトレースを載せる。1 行だけでは、どこで、なぜ、どのコードが原因かが分からない。発生したエラー（スタックトレース）、原因（エラーを出したコードと理由）、解決（直したコードと、なぜ直るか）の順にする
- 記事のサンプルコードには、実務のコードより多めにコメントを入れる。初心者に意図が分かりにくい処理、記事の主題ではないが理解に要る処理、コードだけでは目的が分からない箇所に入れる。読み手が分かることまでは説明しない。基準は「想定した読み手がこのコードを見て疑問に思うか」。実務のコードの「コメントは原則書かない」規則は記事のサンプルには当てはめない
- コードの一部を抜き出すときは、省いたことをコメントで示す（`# 略...`、Go なら `// ...`）。コメントの外に `略...` と書くと、文法エラーに見える

## 9-3. サンプルコードを作る

- 実務のコードや社外秘のコードをそのまま貼らない。ロジックを単純にし、説明に要る部分だけを再現したコードにアレンジする。アレンジしたコードは実務のコードとは別物なので、実際に動くか、ロジックに不自然な部分がないか、誰も見たことのないような書き方になっていないか、生成 AI に任せた部分を自分で確かめたか、を載せる前に確かめる
- メールアドレスや URL には、架空のつもりの実在しそうなドメイン（`hoge.com` など）を使わない。実在するドメインだと、サンプルを実行した人の手元から意図しない相手にメールや要求が送られる。例示用に予約されている `example.com`、`example.net`、`example.org`、`example.edu` を使う
- コピーしてすぐ実行できるコードにする。`require`、`import`、`include` など、動かすのに要る行も含める（`Date.today` だけでなく `require 'date'` も書く）。大きなプログラムの一部を抜き出したときや、実務のコードをアレンジしたときなど、コピーだけでは動かせない場合は、その前提を書く
- 変数名、関数名、クラス名は、役割が読み取れる名前にし、実践的な使い方を題材にする（`Foo` の `hoge` ではなく `Printer` の `print`）。ごく単純な文法や関数の仕様だけを説明するときは、`foo` や `bar` の方が本質から気がそれずによいこともある
- その技術の便利さ（技術のおいしさ）が伝わる使い方を選ぶ。文法として正しいだけの例ではなく、その技術を使う理由がコードから分かる例にする（正規表現の後読みなら、`abc` の `bc` ではなく、`type=zip; filename=users.zip; size=1024;` からファイル名だけを取り出す）
- 難しい内容は、読み手が分かる最も単純な形から始め、要素を少しずつ足して目的の知識にたどり着かせる（RSpec なら、`it` が 1 つの例 → 例を足す → `describe` で一段深くする）。全部入りのコードを先に見せて部品を説明する形にしない
- セキュリティ上問題のあるコードを載せない。初心者は検証せずにコピーする。「こうすれば動く」だけでなく、その方法が安全かを確かめる（Rails で本番に詳しいエラーを出すために `config.consider_all_requests_local = true` を勧めると、内部の情報が攻撃者に漏れる）
- 安全かどうかは、詳しい人にレビューを頼む、生成 AI にレビューを頼む、個人ブログや Q&A サイトだけでなく公式の情報で裏を取る、本でセキュリティを学ぶ、フレームワークのセキュリティの解説を読む、コードの問題を見つけるツールを使う、で確かめる。誤った方法を「便利な解決策」として広めると、似た記事が増えて誤りが広がる

サンプルコードを載せる前に、次をすべて確かめる。

- 説明と実行結果が一致している
- 実際に動かして確かめた
- 試せるだけの依存関係と前提を示した
- 架空の API や関数を、実在するように見せていない
- 外に影響しうるデータには、例示用のドメインなど安全な値を使った
- 名前と使い方から、コードの目的が読み取れる
- 技術を使う利点が、例から分かる
- 難しい内容は、単純な例から段階的に発展させた
- 初心者がコピーしても危ない設定や実装にならない
- 確かでない方法を紹介するときは、公式の情報かレビューで正しさと安全を確かめた

## 10. Markdown の書き方

投稿先で使える記法は違うので、最後は投稿先の仕様を確かめる。

- 見出しは `##` から始める。`#` は記事のタイトルに使われる
- 箇条書きはハイフン、コードはバッククォート 3 つで囲み、言語名を付けて色を付ける
- 本文中の変数名やメソッド名はバッククォート 1 つで囲む
- リンクは `[表示する文字](URL)` で書く。URL だけを 1 行に置くと、Zenn や Qiita ではリンクカードになる
- 段落は空行で分ける。単なる改行の扱いはサービスで違う
- 技術ブログでは、段落の中でも 1 文ごとに改行する。画面の幅が狭いブラウザで、行頭から行末まで視線を動かす距離が減る。ただし読点の位置で改行しない。画面の幅が変わると意図しない位置でさらに折り返されるので、文の中の折り返しはブラウザに任せる

## 11. 正しい情報を正しく伝える

誤った情報を書くと、読んだ人がそれを使い、さらに広げる。技術情報はネットで再利用されやすいので、書き手と読み手の両方が損をする。
記事にするのは「自分が見つけた情報」ではなく、「いまの対象の環境について根拠を確かめた情報」にする。

公式の情報源を確かめる。

- 誰かの記事で解決したときも、公式の情報で、その方法の意味、制約、副作用（性能の低下など）を確かめる
- 生成 AI の回答も正しいとは限らないので、公式の情報で確かめてから使う

OSS なら、コード、Issue、プルリクエストまで確かめる。

- コードを読み、必要ならデバッグ実行して、なぜその処理になるか、何が原因でエラーになるか、どの条件で挙動が変わるかを確かめる
- Issue とプルリクエストで、困っている人の議論、仕様変更の理由、バグ修正の背景、実装上の判断を確かめる

情報の日付とバージョンを確かめる。

- 参考にした記事の投稿日、更新日、対象バージョンを見て、「当時の情報がいまも有効か」を公式の情報と照らし合わせる（例：Ruby の DateTime は 2.5 以降で非推奨で、Time が推奨されている）
- 記事で説明する挙動は、どのバージョンで確かめたか、どのバージョンから変わったか、いまのバージョンではどうかを、分かる範囲で書く
- 実行環境とバージョンを明記する。すべての記事を最新に保つのは難しいので、将来の読み手に「いまの環境とは違うかもしれない」と伝えるために書く

一次情報とそれ以外を区別する。

- 一次情報：公式ドキュメント、ライブラリの README、開発者自身のブログ。GitHub の Issue とプルリクエストもそれに近い
- 一次情報以外：Qiita や Zenn の記事、個人ブログ、生成 AI の回答。更新されずに古くなることがある
- 一次情報なら必ず正しい、それ以外なら必ず誤り、ではない。一次情報以外だけに頼らず、できるだけ一次情報までさかのぼる

参考文献のリンクを残す。

- 読み手が、さらに調べる、別の情報源と照らし合わせる、公式で正しさを確かめる、原典から追加の情報を得る、をできるようにする
- どの情報を参考にしたかを明らかにする。記事の末尾にまとめても、関係する箇所の直後に置いてもよい

その技術に詳しい人がいれば、公開前にレビューを頼む。理解が合っているか、誤解を招かないか、より正確な言い方がないかを聞く。必須ではない。

調べ尽くしても断定できない部分は、不確かであることを書く（例：「この方法が最善か自信がないので、よい方法があればコメントで教えてください」）。
ただし、断り書きは誤りを書いてよい理由にはならない。調べたうえで判断できない箇所に限って使う。公開後に誤りを指摘されたら、確かめて直す。

固有名詞は公式の表記に合わせる（JAVA ではなく Java、Github ではなく GitHub、VisualStudio Code ではなく Visual Studio Code、Mac OS ではなく macOS）。迷ったら公式サイトで確かめる。表記の誤りは記事全体の信頼を下げる。

他の記事、本、公式ドキュメントの文章を使うときは引用として扱う。

- 引用部分を `>` で囲み、自分の文章と区別する
- 元の文章を改変しない
- 出典（タイトルとリンク）を書く
- 記事の主体は自分の文章にし、引用を主体にしない

公開前は、次の順に確かめる。

1. 記事の中の技術的な主張を洗い出す
2. 公式ドキュメント、README、ソースコードなどの一次情報で確かめる
3. 必要なら Issue とプルリクエストで背景や変更の理由を確かめる
4. 参考にした記事の投稿日と対象バージョンを確かめる
5. 自分の環境で動かして確かめる
6. 実行環境と対象バージョンを記事に書く
7. 参考にした情報源へのリンクを残す
8. 不確かな箇所は、その範囲を書く
9. できれば詳しい人にレビューを頼む
10. 固有名詞の公式の表記を確かめる

## 12. 時点と前提を明確にする

日付は、本文でもタイトルでも年まで書く（「4月22日〜24日」ではなく「2026年4月22日〜24日」）。
数年たつと月日だけでは何年のことか分からず、読み手に投稿日を確かめさせることになる。

「現時点では」「今は」「まだ」のような相対的な時点の表現は、書き手と読み手の「いま」がずれるので、具体的な年月を添える（「現時点（2026年3月）では」）。
記事全体が同じ時点のことなら、実行環境の近くに「2026年9月に確かめた」と 1 か所書いてもよい。

エッセイや意見の記事、どちらを選ぶかを勧める記事では、結論が前提条件で変わる。
意見の前に、次のうち解釈に要るものを書く。

- 読み手、対象者
- 会社やチームの状況、普段の働き方
- 書き手の経験と背景（例「Java と C# を長く使ってから Ruby に移った」）。詳しい自己紹介ではなく、内容を解釈するのに要る背景だけにする
- その意見が成り立つと考えている条件

反対意見が予想できるテーマでは、異論があることを冒頭で認め、そのうえで自分の立場と理由を書く（「自分は A がよいと思うが、B を好む人も一定数いる」）。
これは事実として短く書く譲歩で、書き手の立場を守るための弁明ではない（japanese-tech-writing の「著者の立場の弁明を書かない」と両立させる）。

思ったことをそのまま書かない。自分の考えを正しいと感じるほど、違う考えの読み手を説得しようとして文章が攻撃的になる。書く前に、次の段階を挟む。

1. 「自分はこう思っている」と認める
2. 「これを読んだ人はどう思うか」を考える
3. 「自分と違う考えの人が読んでも、主張の理由を理解できるか」を考える
4. そのうえで書く

意見を消すためではなく、読み手の反応を想像して、伝わる形に変えるための段階にする。

技術記事では、内容が正しいことに加えて、次の状態にする。

- 誤解を招かない
- 前提条件が明確
- 時点が明確
- 読み手が検証できる
- 立場の違う読み手にも、主張の理由が分かる

意見の記事では、事実と意見を分け、どの前提、経験、条件からその結論に至ったかを読み手が追えるようにする。

## 13. 公開前の確認

書き終えたら、そのまま公開せず、初めて読む読み手になったつもりで読み直す。執筆中の読み直しは書き手としての確認になりやすい。
次を探し、2〜3 回読み直す。

- 日本語として分かりにくい箇所
- 説明なしで突然出てくる専門用語
- 要らない画像、ふさわしくないスクリーンショット
- 読み手が途中で疑問を持ちそうな箇所

スマートフォンでも下書きを開いて読む。Zenn は下書きを push し、スマートフォンでログインして記事の管理画面から下書きを開く（Qiita は編集画面のプレビューか限定共有）。
表示が変わるので新しい目で読め、ほかのアプリがなく記事に集中でき、小さい画面で読みにくいスクリーンショットや文に気づきやすく、書き手から読み手に切り替えやすい。

タグ（Zenn ではトピック）は、記事の分類、検索、発見に使われる。

- 上限があるので、記事の中心の技術から順に付ける
- 方言のある技術は、実行環境も付ける（SQL なら PostgreSQL、正規表現なら Ruby）
- 表記ゆれ（PostgreSQL、postgres、postgresql10）があるときは、記事数が多い、読み手が実際に使っている表記を選ぶ。Zenn は `https://zenn.dev/api/topics/<名前>` で記事数を確かめられる
- バージョン付きのタグは、バージョンの差が大きい、特定のバージョンでだけ役立つ、ほかに合うタグが無く枠が余っている、のどれかのときだけ使う
- 既存のタグがあるのに別の表記で新しく作らない。記事が分散して見つかりにくくなる

関連する過去の記事があれば、末尾に「あわせて読みたい」の節を作ってリンクする。関連の薄い記事を並べず、この記事を読んだ人の次に役立つものを選ぶ。

公開前に設定できる項目も決める。Zenn はアイキャッチの絵文字を記事の内容に合わせる。はてなブログはカテゴリー（ブログの中だけの分類）とアイキャッチ画像を決める。アイキャッチは SNS でシェアされたときの第一印象になるので、見え方を確かめる。

最後に、次をすべて確かめる。

- 誤字や明らかな誤りがないか
- 読み手が理解しにくい箇所がないか（`reader-test` で、書いた文脈を持たない読み手として読ませる）
- 検索や SNS で記事を見つけた第三者が読んでも分かるか
- 書いた直後は自分の文章を客観的に読みにくいので、できれば時間を置いて読み直す
- タイトル、はじめに、まとめが同じ主題か
- トピック（Qiita ならタグ）に、扱った言語、フレームワーク、ライブラリの名前を入れたか。トピックをフォローしている読み手に届く
- 4 条件（わかりやすい、正確、根拠をたどれる、独自性）を満たすか
- 11 の確認の順番（技術的な主張の洗い出しから、固有名詞の表記まで）を終えたか
- 日付に年があり、「今は」「まだ」などの時点に年月が添えてあるか。意見には前提と背景があるか（12）
- PC とスマートフォンの両方で表示を確かめたか

## 14. 公開した後

新着や検索からの流入を待つだけでなく、自分から告知する。

- SNS では URL だけでなく、記事の具体的な中身と、誰に役立つかを添える（「生成 AI をコーディングに使い始めた初心者向けに、注意したい点をまとめました」）
- 反応が少なければ、中身がより伝わる文に変えて、もう一度シェアする
- 社内の Slack や技術コミュニティでも共有する。記事を書くきっかけになった人や、そのテーマで質問していた人には特に届ける価値がある。詳しい人からの指摘、誤りの訂正、新しい知識、同じ技術に興味がある人とのつながりが得られる
- イベントについて書いたら、イベントのハッシュタグを付ける

共有の投稿は、ユーザー本人の名義で出るので、文面を提示して承認を得てから投稿する。業務の場所（社内の Slack など）に共有するかは、公開範囲の規則（個人のリポジトリ名や私的な教材を業務の場所に書かない）に照らしてユーザーが決める。

公開の曜日と時間帯も考える。平日なら、SNS を見る人が比較的多いと考えられる朝（7:00〜9:00）、昼（12:00〜13:00）、夜（仕事や帰宅の後）が候補になる。
夜は、シェアが徐々に広がって一定時間後に大きく伸びる場合の時間を確保しやすい。土日と祝日は平日より SNS を見る人が少ないことがあるので、多くの人に届けたいなら平日も選択肢になる。
読み手の層と媒体で最適な時間は違うので、決まった正解としては扱わない。
Qiita の週間ランキングを狙うなら、集計の期間が長く取れる月曜日の公開を検討する。

公開後も改善する。

- 「中身が分かりにくい」という反応があれば、告知文を直す
- 技術的な指摘を受けたら、確かめて記事を直す
- 反応を見て、タイトルや説明を見直す
- 技術や仕様が変わったら、内容を更新する
- 自分の記事を読み直して気づいた点を直す
- 他の人の技術記事を読み、参考になったものにはリアクションを返す

公開した後に読み直すと、執筆中に気づかなかった、読みにくい文、説明の不足、誤字、技術的な誤り、分かりにくい箇所が見つかる。
内容が変わる修正や情報の追加をしたら、いつ、どこを変えたかを本文に書く（例「2026年9月23日 追記：○○の仕様変更に合わせて説明を更新しました」）。以前読んだ人が変更に気づける。記事をストックした読み手に変更を通知できるサービスでは、大きな変更のときに使う。

過去の記事も、いまも役立つ、最近フォローした人に届いていない、いまの話題と関係する、のどれかなら、あらためてシェアする。同じ投稿を繰り返さず、「昔書いた記事です。○○で困ったときの調べ方をまとめています」のように、過去の記事であることと、いま読む価値を書く。

技術記事は、ライブラリの仕様変更、新しい API の登場、非推奨化、バグの修正、より良い実装の登場で古くなる。古い記事を定期的に見直して更新する。

- 公開時と最新版で仕様が変わったら、古い説明を消すだけでなく、経緯が役立つなら追記で残す（「2026年11月30日 追記：○○ v2.14.0 からこの機能が使えるようになりました。最新版ではこちらの方法を使えます」）。読み手が、当時の状況、変わった仕様、いまの推奨を時系列で追える
- バグや一時的な制約について書いた記事は、その問題がいまも残っているかを確かめ続ける。GitHub の OSS なら、関係する Issue とプルリクエストを Subscribe して、修正とマージを追う。解決したら、直ったバージョン、時期、いまは起きないこと、必要なら新しい実装を追記する
- 公開後に学んだことが記事の主題と一致するなら、新しい記事を作らずに追記してよい。知識を集めた記事は、追記を重ねて育てられる

大きく更新したら、変更の通知機能、SNS、社内やコミュニティで知らせる。「以前公開した記事を更新しました。○○の最新版への対応を追記しています」のように、何が変わったかを書く。

公開した後は、次の循環で記事を保つ。

1. 公開する
2. SNS やコミュニティで共有する
3. 読み手の反応と、技術の変化を確かめる
4. 自分でも読み直す
5. 加筆、修正する
6. 変更を知らせる
7. 必要なら、もう一度共有する
