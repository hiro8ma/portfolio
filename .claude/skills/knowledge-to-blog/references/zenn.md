# Zenn の原稿の書き方

## 置き場とファイル名

`../zenn/articles/<slug>.md` に置く。
slug はファイル名そのもので、`a-z0-9` とハイフンとアンダースコアで 12〜50 文字。
URL の一部になり、後から変えると URL が変わる。題材を表す英語で付ける。

## frontmatter

```yaml
---
title: "session.state に代入しても保存されない — ADK の State を実物で測った"
emoji: "🧪"
type: "tech"
topics: ["adk", "python", "go", "aiagent"]
published: false
---
```

| 項目 | 決め方 |
| --- | --- |
| `title` | 結論か、問いと結論を入れる。数字は本文の実測値そのまま |
| `emoji` | 絵文字 1 つ。一覧で記事を見分ける目印になる |
| `type` | 技術の実測や実装は `tech`、組織論や考え方は `idea` |
| `topics` | 英小文字と数字だけで 5 個まで。記事で扱う言語、フレームワーク、ライブラリの名前を先に置く。トピックをフォローしている読み手に届く |
| `published` | 常に `false`。公開はユーザーが Zenn の画面で判断する |

`published_at` は付けない。一度入れると変えられない。

## portfolio の記事との違い

| 観点 | portfolio | Zenn |
| --- | --- | --- |
| 読み手 | 業界の動きを追う人 | 手を動かす開発者 |
| 構成の中心 | 何が起きたか、日本への示唆 | 何を確かめ、実物がどう動いたか |
| 記法 | MDX | Markdown と Zenn 独自の記法。MDX は使えない |

Zenn の読み手は再現したい人が多い。
「測り方」の節と、実行したコマンドと、実際の出力を省かない。

## Zenn 独自の記法

使いどころを絞る。多用すると本文の流れが切れる。

```markdown
:::message
補足や前提。本文の流れから外したい注意を 1〜2 文で書く
:::

:::message alert
読み手が踏むと困る落とし穴。確かめた事実だけを書く
:::

:::details 実際の出力（長いので折りたたみ）
長いログや全文はここに入れる
:::
```

コードブロックにはファイル名を付けられる。

````markdown
```python:samples/memory/agent.py
root_agent = build_agent()
```
````

## 画像

画面の機能を説明するときは、機能ごとにスクリーンショットを撮って貼る。
文章だけで UI を説明すると、読み手は同じ画面を探せない。

- 置き場は `../zenn/images/<slug>/<機能名>.jpg`。1 枚 3MB まで
- 本文では `![代替テキスト](/images/<slug>/<機能名>.jpg)` と書く
- 代替テキストは省かない。画像が表示されない読み手にも、何の画面か伝わる文にする
- 自分で操作して撮った画面だけを使う。撮っていない画面の説明は「確かめていない」と書く
- 写り込み（API キー、個人のアカウント名、社内の URL）を貼る前に確かめる

## 組織論（type: idea）を書くとき

組織論の素材は業務の議事録や数値から来ることが多い。
社名は禁止語で拾えるが、社内の数値（担当社数の目標、コスト率、人数）は文字列では拾えない。
手順 2 の仕分けで、数値は「公開の資料にあるもの」か「一般的な水準として示せるもの」だけに絞る。

主張は、経験した事実と、そこから引いた判断に分けて書く。
事実の側に固有の状況が残りやすいので、判断の側を厚くする。
