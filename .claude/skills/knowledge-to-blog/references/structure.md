# 測定ノートからブログ記事への構成

## ナレッジの節と記事の節の対応

| ナレッジの節 | 記事の節 | 書き換えるときの注意 |
| --- | --- | --- |
| frontmatter の `book` | 書かない | 教材名は参考リンクへ。私的な学習教材であることは書かない |
| TL;DR | `description` と冒頭の 1〜2 段落 | 冒頭は結論から。「実物は教材と違った」のような発見を先に置く |
| 教材の流れ / 前提 | 「何を確かめたか」 | 読み手は教材を読んでいない前提で、主張だけを 1〜2 文で示す |
| 実物と突き合わせた結果 | 本文の中心 | 教材の記述と実測を表で並べる |
| 食い違った点 | `###` の小見出し 1 つずつ | 見出しだけで何が違ったか分かる形にする |
| 測り方で守ったこと | 「測り方」節 | 再現したい読み手に最も効く。省かない |
| 面接で話すなら | 書かない | 私的な用途の節なので記事には持ち込まない |
| 自分の実装との接続 | 「実務での判断」 | 業務の固有名は外し、判断の型として書く |
| 関連（`[[...]]`） | 書かない | 公開済みの記事があれば、その記事へのリンクに置き換える |

## 書く前の下調べとアウトライン

ナレッジに書いてあることでも、記事にする前に次を確かめる。
- 公式ドキュメントを読み、自分の理解と一致しているか
- 小さいサンプルを動かし、予想どおりに動くか
- ライブラリのコードを読み、なぜその挙動になるか
- 仕様が変わった理由は、GitHub の Issue とプルリクエストで確かめる

調べる途中で「なぜそうなっているのか」という問いが出たら、記事の軸をその問いに移すことを検討する。
単なる比較より、理由まで書いた記事の方が読む価値が上がる。

長くなりそうな記事は、本文の前に「書きたいことの一覧」を作り、見出しの親子関係を決めてから書く。
読み手は「その技術を知らなかった数か月前の自分」に置くと、つまずく箇所を思い出しやすい。

## 記事の型

```
## 何を確かめたか
[教材や公式の主張を 1〜2 文。読み手が自分に必要な記事かを判断できるように、対象と前提を書く]

### 実行環境
[言語 / ライブラリ / OS / モデルのバージョンを箇条書き。挙動が変わりうるものは全部]

## 結果
[実測の表。教材の記述と並べる]

## <食い違い 1 を 1 文で言う見出し>
[再現コード 5〜20 行 → 実際の出力 → なぜそうなるか（ソースの該当箇所）]

## <食い違い 2>
...

## 測り方
[誤測定を避けた工夫。測り直して結論が変わった経緯があれば書く]

## 実務での判断
[この結果を受けて、どう設計・運用を変えるか]

## まとめ
[3〜5 個。「説明しました」で終えず、読み手が持ち帰る判断を書く]

## 参考リンク
```

## タイトルの付け方

測定記事は「問い + 結論」か「現象 + インパクト」の型が合う。

| 型 | 例 |
| --- | --- |
| 問い + 結論 | `temp: は本当に消えるのか — ADK の State が保存される経路を測った` |
| 現象 + インパクト | `Go の SIMD で全探索を 10 倍速に — ルーフラインの天井を測るベンチが壊れていた` |

数字は実測値をそのまま使う。丸めた数字を見出しに置くと、本文の表と食い違う。

タイトルは本文を書き終えてから、本文の要約として決め直す。
タイトルは検索結果やタイムラインで単独で表示される前提で作る。

- 対象の技術名を入れ、前半に置く。後半は一覧で省略されることがある
- 読むと何が分かるか、何ができるかを入れる。数値（何個、何回、何か月）があれば使う
- 誰向けかが本文から一意に決まるなら、それも入れる
- 本文が応えられない強い約束や煽り（「知らないと損」「最強」）は入れない
「ADK の State」のような対象だけのタイトルにせず、現象か問いを入れて、読まなくても何の記事か分かる具体さにする。

## はじめにとまとめ

はじめには記事の行き先を示す。
何を説明するか、読むと何が分かるか、誰向けか、前提知識は何かを、冒頭の数段落で読み手が判断できるようにする。

まとめは目的地に着いたことを示す。
何が分かったかを 1〜2 文で言い直し、長くしない。

書き終えたら、タイトル、はじめに、まとめが同じ主題を扱っているかを確かめる。
書く途中で主題が変わったら、本文だけでなく 3 つとも最終的な中身に合わせて直す。

長く複雑な記事には、冒頭に TL;DR を 3〜5 個の箇条書きで置く。書き終えてから、長くなったと判断した時点で足してよい。
全文を読まなくても持ち帰ってほしい結論を書き、記事の構成の紹介にはしない。

本文とコードは、コードの前後で「何を実現するコードか」「どこを見るか」「変更前後で何が変わったか」「なぜこの書き方か」を書き、コードだけを並べない。
割合は文字数でコードと本文が半々前後を目安にする。厳密な基準ではなく、コードを大量に貼って説明が数行しかない状態と、説明だけで実装が想像できない状態の両方を避けるための目安にする。

画像や動画は、文章では伝えにくいものに使う。

- 画面の操作、UI の状態、コードの変更による画面の変化はスクリーンショットにする
- 時間の変化そのものを見せたいときだけ、動画か短いアニメーション GIF にする。GIF は大きくなりやすいので範囲と解像度を絞る
- 抽象的な関係は図にする。作図の道具は問わない
- コードは原則テキストで載せる。矢印や書き込みで示したいときだけ補助的に画像にし、テキストのコードも残す
- スクリーンショットは見せたい範囲に絞り、文字が読める大きさで撮る。縦に長い画像は折りたたむ
- 貼った後に、スマートフォンの幅でも読めるかを確かめる

抽象的な主張は、書き手の実体験（何をして、何が起き、何が分かったか）に落として具体例にする。
本文中の絵文字や「ハマる」「〜ですよね」のような口語は、測った事実を伝える記事では外し、観測と判断をそのまま書く。

## 仕組みを説明するときの型

記法や挙動の仕組みを説明する節は、次の順で組む。

- 読み手と焦点を先に絞る。「Go で書く人向けに、Python の資料と違うところだけ」のように、何を説明しないかも決める
- 読み手が抱く疑問は、最初のコード例のコメントに疑問文のまま書く。答えは本文で説明し、一語で答える問答の形にしない
- 省略した書き方と、省略しない書き方を並べる。同じ意味になることをコードで見せる
- 見た目が似たものは並べて、違いを示す
- 節の最後に、見かけた書き方ごとに意味を引ける表を置く。「やること」の一覧ではなく「見分け方」の一覧にする

```ruby
# name: の ":" って何だろう？
user_data = { name: 'Alice' }
# 省略しない書き方。上と同じ意味
user_data = { :name => 'Alice' }
```

## 実測を書くときの型

教材と実物が違った場合は、両方を並べてから理由を書く。

```markdown
教材は `session.state["user:name"] = "田中"` で保存できると書く。
実際に書き換えてから取り直すと、値は元のままだった。

| 操作 | 期待 | 実測 |
| --- | --- | --- |
| 直接代入 | 保存される | 保存されない |
| state_delta を載せたイベント | 保存される | 保存される |
```

理由はソースの該当箇所か、切り分けの実験で示す。
推測で埋めない。

エラーを扱うときは、エラーメッセージを加工せずに貼る。
同じエラーで検索した読み手が記事にたどり着ける。
