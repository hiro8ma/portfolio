# 測定ノートからブログ記事への構成

## ナレッジの節と記事の節の対応

| ナレッジの節 | 記事の節 | 書き換えるときの注意 |
| --- | --- | --- |
| frontmatter の `book` | 書かない | 教材名は参考リンクへ。私的な学習教材であることは書かない |
| TL;DR | `description` と冒頭の 1〜2 段落 | 冒頭は結論から。「実物は教材と違った」のような発見を先に置く |
| 教材の流れ / 前提 | 「何を確かめたか」 | 読み手は教材を読んでいない前提で、主張だけを 1〜2 文で示す |
| 実物と突き合わせた結果 | 本文の中心 | 教材の記述と実測を表で並べる |
| 食い違った点 | `###` の小見出し 1 つずつ | 見出しだけで何が違ったか分かる形にする |
| 測り方で守ったこと | 「測り方」節 | 再現したい読み手に最も効く。省かない |
| 面接で話すなら | 書かない | 私的な用途の節なので記事には持ち込まない |
| 自分の実装との接続 | 「実務での判断」 | 業務の固有名は外し、判断の型として書く |
| 関連（`[[...]]`） | 書かない | 公開済みの記事があれば、その記事へのリンクに置き換える |

## 記事の型

```
## 何を確かめたか
[教材や公式の主張を 1〜2 文。読み手が自分に必要な記事かを判断できるように、対象と前提を書く]

### 実行環境
[言語 / ライブラリ / OS / モデルのバージョンを箇条書き。挙動が変わりうるものは全部]

## 結果
[実測の表。教材の記述と並べる]

## <食い違い 1 を 1 文で言う見出し>
[再現コード 5〜20 行 → 実際の出力 → なぜそうなるか（ソースの該当箇所）]

## <食い違い 2>
...

## 測り方
[誤測定を避けた工夫。測り直して結論が変わった経緯があれば書く]

## 実務での判断
[この結果を受けて、どう設計・運用を変えるか]

## まとめ
[3〜5 個。「説明しました」で終えず、読み手が持ち帰る判断を書く]

## 参考リンク
```

## タイトルの付け方

測定記事は「問い + 結論」か「現象 + インパクト」の型が合う。

| 型 | 例 |
| --- | --- |
| 問い + 結論 | `temp: は本当に消えるのか — ADK の State が保存される経路を測った` |
| 現象 + インパクト | `Go の SIMD で全探索を 10 倍速に — ルーフラインの天井を測るベンチが壊れていた` |

数字は実測値をそのまま使う。丸めた数字を見出しに置くと、本文の表と食い違う。

タイトルは本文を書き終えてから、本文の要約として決め直す。
「ADK の State」のような対象だけのタイトルにせず、現象か問いを入れて、読まなくても何の記事か分かる具体さにする。

## 仕組みを説明するときの型

記法や挙動の仕組みを説明する節は、次の順で組む。

- 読み手と焦点を先に絞る。「Go で書く人向けに、Python の資料と違うところだけ」のように、何を説明しないかも決める
- 読み手が抱く疑問は、最初のコード例のコメントに疑問文のまま書く。答えは本文で説明し、一語で答える問答の形にしない
- 省略した書き方と、省略しない書き方を並べる。同じ意味になることをコードで見せる
- 見た目が似たものは並べて、違いを示す
- 節の最後に、見かけた書き方ごとに意味を引ける表を置く。「やること」の一覧ではなく「見分け方」の一覧にする

```ruby
# name: の ":" って何だろう？
user_data = { name: 'Alice' }
# 省略しない書き方。上と同じ意味
user_data = { :name => 'Alice' }
```

## 実測を書くときの型

教材と実物が違った場合は、両方を並べてから理由を書く。

```markdown
教材は `session.state["user:name"] = "田中"` で保存できると書く。
実際に書き換えてから取り直すと、値は元のままだった。

| 操作 | 期待 | 実測 |
| --- | --- | --- |
| 直接代入 | 保存される | 保存されない |
| state_delta を載せたイベント | 保存される | 保存される |
```

理由はソースの該当箇所か、切り分けの実験で示す。
推測で埋めない。

エラーを扱うときは、エラーメッセージを加工せずに貼る。
同じエラーで検索した読み手が記事にたどり着ける。
